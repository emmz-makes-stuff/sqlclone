# sqlclone

A `dotnet tool` that clones a SQL Server database (every object and all of its data) onto another server under a
new name.

```sh
sqlclone --source "Server=src,1433;Database=Sales;User Id=sa;Password=...;TrustServerCertificate=True" \
         --target "Server=dst,1433;User Id=sa;Password=...;TrustServerCertificate=True" \
         --name   Sales_Copy
```

| Option | | |
|---|---|---|
| `-s`, `--source` | required | Connection string for the source database. It must name the database. |
| `-t`, `--target` | required | Connection string for the target server. Any database in it is ignored. |
| `-n`, `--name` | required | Name of the new database on the target server. |
| `-f`, `--force` | | Drop the target database first if it already exists. Without it, an existing database is an error. |
| `-p`, `--parallelism` | default `4` | Number of tables copied at the same time. |

Exit codes: `0` success; `1` the clone could not run (connection failure, target exists, ...); `2` the clone ran
but some objects failed, and each one is listed on stderr.

## Install

```sh
dotnet pack src/SqlClone -c Release          # writes artifacts/SqlClone.<version>.nupkg
dotnet tool install --global SqlClone --add-source ./artifacts
```

## A SQL Server to try it against

`compose.yaml` runs a SQL Server 2025 Developer instance on port **1434** (so it runs alongside one already on
1433), with a `sysadmin` login named `emmz`:

```sh
docker compose up -d      # docker compose down -v removes it and its data
sqlcmd -S localhost,1434 -U emmz -P 'S3cr3tSqu!rr3l' -C
```

```
Server=localhost,1434;User Id=emmz;Password=S3cr3tSqu!rr3l;TrustServerCertificate=True
```

The image only creates `sa` (given the same password). A short-lived `init` container adds the `emmz` login once
the server is healthy. `TrustServerCertificate=True` (or `-C` for sqlcmd) is needed because the certificate is
self-signed. In a shell, single-quote connection strings so that the `!` isn't treated as history expansion. The
instance starts empty.

## How it works

1. **Database.** The tool creates the target database with the source's collation and compatibility level.
2. **Schema, before data.** Schemas, XML schema collections, alias and table types, rules and defaults, sequences,
   tables (with primary keys and defaults only), synonyms, functions, views and procedures. SMO scripts the
   declarative objects. Programmable objects are copied verbatim from `sys.sql_modules` together with their
   `ANSI_NULLS`/`QUOTED_IDENTIFIER` settings, so their text matches the source exactly.
3. **Data.** Each table is streamed from source to target with `SqlBulkCopy` (`KeepIdentity`, `KeepNulls`,
   `TableLock`), several tables at a time. No foreign keys, check constraints, secondary indexes or triggers exist
   on the target yet, so nothing slows the load down and no rows get rejected.

   A bulk load stores every `(max)` value off-row behind a pointer of roughly 26 bytes, even a tiny one. So a very
   wide table (the sample has one with 1,012 `nvarchar(max)` columns) can fail with error 511 even though each row
   fit when it was inserted normally. When that happens, the tool copies that one table with batched, parameterized
   `INSERT`s, which store rows the same way the source did, and prints a warning.
4. **Schema, after data.** Clustered and non-clustered indexes, unique constraints, user statistics, check
   constraints and foreign keys are created next. Constraints that were trusted in the source are validated again
   (`WITH CHECK`), and disabled ones stay disabled. Then rule and default bindings, DML and DDL triggers (disabled
   ones stay disabled), identity current values, sequence current values and extended properties.

Each object is created in its own transaction. Objects are created in a natural order, and any that fail because a
dependency doesn't exist yet are retried until a pass makes no further progress, so no dependency graph is needed.

Constraint names are always kept, including system-generated ones (`PK__Table__3214EC07...`).

## Limitations

These are not cloned (a warning names each one that is present):

- CLR assemblies and CLR objects; encrypted modules; full-text catalogs and indexes.
- Users, roles, permissions and server logins.
- Filegroups and partition schemes: everything is created on `PRIMARY`.
- `rowversion` columns get new values, since SQL Server generates them on insert.
- Server-level objects the database depends on (linked servers, logins, other databases referenced by three- or
  four-part name) must already exist on the target. A module that can't compile without them is reported, and the
  run exits with code 2.
- Modules are copied from their stored text. After an `sp_rename`, that text still has the old name, so a renamed
  procedure would be created under its old name (or fail as a duplicate). Recreate renamed modules with
  `CREATE OR ALTER` before cloning.
- Some names are generated by SQL Server and can't be preserved: a table type's internal table, and constraints on
  the return table of a multi-statement table-valued function.
- An identity on a table that is **empty** but has used values (rows deleted) continues from the right value.
  `IDENT_CURRENT` on the clone reports one increment higher than the source, because of how `DBCC CHECKIDENT`
  treats a table that has never had a row.
- Temporal (system-versioned) tables, memory-optimized tables and graph tables have not been tested.

## Development

```sh
dotnet build
dotnet test     # needs Docker; pulls mcr.microsoft.com/mssql/server:2025-latest
```

The integration test starts two SQL Server 2025 containers with Testcontainers:

- **Source.** Runs the Express edition and stands in for SQL Express. Both sample scripts in `samples/` are loaded
  into it. `tests/.../Scripts/Extras.sql` adds a test-only set of objects that the samples lack (non-dbo schema,
  sequence, bound rule, computed/xml/sql_variant/rowversion columns, check and unique constraints, a disabled FK, a
  filtered index, an indexed view, a synonym, a disabled trigger, a DDL trigger, extended properties). Every table
  is then filled with random rows.
- **Target.** Both databases are cloned into it with the CLI.

Loading the samples involves a few workarounds, all in `SqlServerFixture`:

- The scripts separate batches with `;`-only lines instead of `GO`, so `SqlScript` splits them itself.
- The fixture creates the two users that the scripts grant permissions to.
- It skips the few objects in `SRM-Framework.sql` that can't be created anywhere as written: a procedure defined
  twice (the second copy is a renamed `_BACKUP`), two procedures that don't compile ("Ambiguous column name"), and
  three procedures that read tables on linked servers.

The test then compares source and clone by catalog: objects, module text hashes, columns, indexes, keys,
constraints, triggers, types, synonyms, sequences, identity values and extended properties. For data, it compares
a row count and an order-independent SHA-256 per table. On Apple Silicon the image runs under Rosetta.
